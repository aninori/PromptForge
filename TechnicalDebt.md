1. There is no trust boundary — the API is an unauthenticated filesystem-read primitive
Nothing on this server requires auth, and main.py:43-49 combines allow_origins=["*"] with allow_credentials=True — Starlette resolves that combination by echoing back whatever origin calls, so any webpage the operator visits can script this backend from their browser. The chain a drive-by page can execute today:

GET /repo/tree walks any absolute path on the machine — C:\Users\nsani\.ssh, anything. There is no root confinement, only a cosmetic skip-list.
POST /index will happily embed any directory into Chroma, and /query will then summarize its contents on demand. That's arbitrary file exfiltration with extra steps.
PATCH /config lets the caller set ollama_url — point it at an attacker's server and every subsequent embed/chat call ships query text and code chunks off-box. Unauthenticated SSRF plus data exfiltration in one request.
At 1x traffic this is a loaded gun on localhost; at 10x (i.e., the moment this is deployed anywhere reachable) it's a breach. Fix: pin CORS to the frontend origin, require a bearer token on every mutating endpoint, and confine /repo/tree and /index to an allowlisted workspace root. That's a day of work.

2. The GitHub token is written to disk in plaintext, permanently
github_integration.py:156-161 injects the OAuth token or PAT into the clone URL, and clone_or_update then runs git remote set-url origin <token-url> — which persists https://x-access-token:TOKEN@github.com/... into .git/config on disk, where it survives restarts, backups, and the in-memory "single-user token store" the module's own comment brags about. The token also appears in argv of every git subprocess, visible to any process listing on the box. The error-message scrubbing at line 173 shows someone thought about leakage and still missed the two big sinks. With scope=repo (line 72), that token is read/write on every private repo the user has. Fix: pass credentials per-invocation via git -c credential.helper= + GIT_ASKPASS or http.extraHeader, and never store them in the remote URL.

3. Global mutable state + a fully synchronous pipeline — this architecture caps out at roughly 40 concurrent users, then everything stops
Three compounding problems, one root cause (single-process, shared-everything design):

Every handler is sync def, so FastAPI runs them on the default ~40-thread pool — including the SSE generators in _stream_pipeline and agent streaming, each of which pins a thread for the entire multi-second generation. At 10x traffic the pool exhausts and even /health queues behind LLM calls. The whole service brownouts, not just queries.
PATCH /config mutates the live settings singleton (config.py:69) that in-flight requests are concurrently reading — a request can start on Ollama and finish billing tokens against Groq. And with multiple uvicorn workers, the PATCH only lands on one worker, so config becomes nondeterministic per request. Same story for ConversationMemory._sessions (unbounded, never evicted — a slow memory leak per session-id) and _connected in the GitHub module.
Unsynchronized read-modify-write everywhere state persists: /feedback does get-then-update per chunk with no lock (concurrent votes lost), and index_repo can run simultaneously from the watcher thread, a webhook, and a manual /index — all rewriting file_hashes.json, the BM25 pickle, and doing graph_memory.reset_graph() on shared globals. Two concurrent index runs will corrupt each other's output silently.
Fix direction: make the pipeline async (or at minimum bound and separate the LLM threadpool from the request pool), freeze config per-request at entry, put a single lock around index runs, and move session/connection state behind an interface you can later back with Redis. This is also the same refactor that collapses the triplicated pipeline from my previous review — one root cause, one fix.

Honorable mentions (real debt, not top-three): N+1 Chroma col.get(ids=[cid]) loops in retrieval.py:120 and 147; _evict_oldest doing a full-collection scan on every cache save (cache.py:53); and _link_graph's bidirectional-substring import matching, which creates complete bipartite chunk-edge sets per matched file pair — on a large repo that's a combinatorial graph.json explosion and a flood of false "neighbor" context polluting retrieval.
